# 專案共編紀錄

這個資料夾讓 UI/UX 協作者、系統開發者與各自的 AI 共用同一份交接資訊。目的不只是知道「改過什麼」，也要知道「為什麼這樣設計、哪些成果要保留、哪些地方有人正在改」。

## 先看哪份文件？

| 文件 | 用途 |
| --- | --- |
| [根目錄 AGENTS.md](../AGENTS.md) | AI 修改前、修改中、提交前的共同規則 |
| [DESIGN_DECISIONS.md](DESIGN_DECISIONS.md) | 已確認的產品／設計決策，以及尚未確認的設計提案 |
| [CURRENT_WORK.md](CURRENT_WORK.md) | 目前誰在做什麼、涉及哪些檔案、是否重疊 |
| [HANDOFF.md](HANDOFF.md) | 待確認、待串接、需要接手的問題 |
| [changes/](changes/) | 每次修改各自一份 MD，不共寫一份無限增長的大日誌 |
| [修改紀錄範本](templates/CHANGE_RECORD.md) | 每次新增紀錄時複製使用 |

## 每次工作的流程

1. 先同步資訊：讀規則、決策、分工、交接及相關修改紀錄；確認本機和遠端 Git 差異。未提交檔案也可能是別人的成果，不能當成垃圾清除。
2. 登記本次範圍：例如「只改免費列印頁的按鈕尺寸，不改 API」，不要只寫「前端」或「後端」。登記基準 commit；他人正在處理相同檔案時，先釐清哪些區塊可以各自改。
3. 在最新內容上小範圍修改。若需要更改已確認設計，先說明衝突並依使用者方向更新決策。
4. 驗證修改後新增紀錄、更新交接及分工，再依授權提交。紀錄和程式碼應在同批提交，不要只留在 AI 對話裡。
5. 提交／推送前再核對一次遠端。如果有人剛推了新版本，先檢視差異；不能以強制推送把對方的提交刪掉。

## 怎麼保護「他改好的圓角」？

修改紀錄記下本次改動；若這是使用者／團隊已確認、後續應維持的設計，再加一筆設計決策，例如：

> 以下只是填寫示例，**不是目前已確認的設計**：`D-UI-範例`，會員工作台主要按鈕採 12 px 圓角，適用某元件與某 token，原因是維持會員操作介面一致，經誰確認、何時確認，並附截圖或提交。

下一個 AI 修報價或 API 時，就要保留這項決策，不能順便把它改成方角。若僅有協作者的提案、尚未被確認，就標「待確認」，不能把提案寫成使用者已批准。

即使沒寫進決策文件，現有 UI 也不是可以隨意覆蓋的空白畫布；預設保留，必要改動仍要看最新程式碼與 Git 差異。

## 紀錄命名與合併

- 建議檔名：`changes/YYYY-MM-DD-工作者代號-主題.md`；日期採 `Asia/Taipei`。同人同日同主題可加 `-02`，避免撞名。
- 檔案中的頁面、元件、token、commit 比「昨天改的那個」更可靠。截圖可附於專案內，或提供團隊可存取的位置；本機暫存位置要註明無法供他人長期存取。
- `changes/` 保留歷史；修正舊紀錄時註明補充日期與原因。設計取代要保留原決策與取代關係，不刪舊理由。
- 共用的決策、分工與交接文件本身也可能衝突，合併時保留雙方條目；文字合併成功不代表設計沒有衝突。

## 分支與安全界線

目前使用者要求成果交付到 `main`。多人同時開發時，建議各自在工作分支完成，再經比對／審查合併到 `main`；工作分支不代表成果留在別的分支。若依使用者要求直接推 `main`，也必須核對遠端、使用小提交，推送遭拒時先查原因，不能 force push。

本次沒有建立分支、PR、CODEOWNERS 或 GitHub 分支保護。文件不是檔案鎖，也無法阻止不遵守規則的工具。若日後需要強制審查，可再討論 GitHub 保護規則與審核人，不預先替尚未確認的協作者設定權限。

## 可以直接交給另一位協作者的話

> 這個專案有共編紀錄。請你的 AI 動手前先讀根目錄 `AGENTS.md` 與 `collaboration/README.md`，確認最新 Git 差異，再看設計決策、目前分工和交接。請保留其他人的 UI/UX，只修改本次範圍；完成後新增一份 `collaboration/changes/` 紀錄，並把確認過的圓角、色彩、間距等決策記下來。
